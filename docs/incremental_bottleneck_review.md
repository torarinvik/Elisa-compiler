# Incremental compilation bottleneck review

Reviewed 2026-10-18 from the local build notes, retained-edit benchmark, compiler LLVM dump, and the Go compiler's ARM64 disassembly.

## What the measurements show

The stage1 build profile in [build-speed-notes.md](build-speed-notes.md) is historical (base `2678ff10`), not a profile of the current working tree. It attributed 46% of samples to semantic analysis, 39% to LLVM IR generation, and 4% to O0 object emission. `check_region_storage_stability` accounted for 17.6% of samples; its `param_growth_rows` and `pgs_callee_fields` work accounted for 9.6% and 7.6%. The current `param_growth_summary.elisa` already has per-round dependency scheduling and indexed callee rows, so that old profile does not justify another isolated lookup tweak. A fresh matching stage1 profile is needed before ranking today's self-hosted hotspots.

Historical default-build measurements in [stage1_performance.md](stage1_performance.md) show a different priority from the O0 object-cache experiments: whole-module LLVM O2 took 92.7 seconds of a 134-second self-host build, and a later round measured 97 seconds of 143 seconds. The associated pass profile covered 2.03 million IR instructions and 9,350 functions; InstCombine was about 20% of pass time, followed by the Inliner at 7.6%. A parallel ThinLTO prototype reduced optimizer-plus-codegen wall time on a loaded host, but the resulting compiler failed runtime parity and was not adopted. These profiles are old Linux snapshots, not current-source measurements. They show why an O0 shard cache alone cannot address the historical default O2 bottleneck, and why O2 reuse needs an optimization boundary that preserves cross-function imports and passes runtime parity.

The available `build/s1_driver.ll` is not usable for machine-code conclusions. Its `Semantic.check_region_storage_stability` wrapper only loads file fields and calls the declaration walker, but Clang rejects the module elsewhere: `%__packed_payload_108` receives an `i64` for an `i32` field at IR line 213991. Consequently the requested `-O0` assembly could not be generated from this dump. Do not use this stale dump as evidence about current generated code.

The saved `build/verification/current-seed-bb0b884b/` attempt is also not a current compiler result. Its 1,186-file input manifest was unchanged during the run, but Stage1 seeding stopped at the default 6 GiB RSS guard (`rc=125`, peak 6,443,352,064 bytes) after lexing in 565 ms and parsing in 2.204 s; it never reached semantic analysis or IR emission. Comparing that manifest with today's tree finds 630 changed inputs. Raising `ELISA_STAGE1_SEED_MAX_RSS_KB` may allow a later stable run to reach actionable diagnostics, but this artifact supplies none.

The source-frozen semantic profile under `build/verification/frozen-seed-profile-bb0b884b/` is useful for allocation leads, but not as a current-source result: it pins the older Core revision `bb0b884b`, exits during semantic analysis before codegen, and reports 223.6 s elapsed. Its CPU profile is dominated by Go heap clearing (`runtime.memclrNoHeapPointers`, 39.5% flat), map assignment (15.1% cumulative), and `madvise` (11.1% flat). Its allocation profile attributes 3.32 GB to `cloneTrackedValueTypeWithSeenDepth`, 2.05 GB to `strings.Builder.WriteString`, 1.30 GB to `strings.FieldsFunc`, 1.15 GB to `abstractParamRegionRefState`, and 6.29 GB cumulatively to `smtCheckVCMulti`. These identify semantic allocation and GC pressure worth re-profiling after a successful, source-matched seed; they do not rank today's LLVM or object-emission path.

## Retained session memory and lifetime

The original session declarations had dynamic arrays and a dictionary without region parameters or per-field region annotations; qualifying only a function's `session` reference did not establish that nested storage survived request teardown. The current worktree now introduces `IncrementalSemanticSession[@r]` and a separate `IncrementalSemanticSessionSnapshot[@r]`, annotates retained collections `@r`, copies portable facts into that snapshot, and leaves invocation anchors in the request-owned snapshot. New controls now cover a generic struct with an empty `darray[...] @r` field that grows through the struct, reject a request-borrowed view stored in a session region, and drive a small-to-128-included-functions-to-same-large sequence through request teardown. The gate compiles the direct field control but does not execute its generated code; the live session sequence requires the repeated large request to hit with at least 100 eligible function bodies, all matched to retained facts. These controls have been reviewed statically but the gate has not yet been run, so the ownership change remains unvalidated by the compiler. The opt-in session remains a semantic-only host. The ordinary CLI now passes a fresh request-scoped session through its compile path, but discards it at request end and cannot reuse facts across separate invocations, so it is not yet an edit-to-executable speedup. Retain no token slices, AST-backed names, or other request views.

There is a separate request-peak issue: candidate scanning stages findings and then staged fact/anchor arrays, while edit replay also stages rebound anchors. A review estimate puts the peak near 176 bytes per finding before allocator growth when those buffers coexist. Reclaim candidate scratch in a nested region, or stream with rollback so a body is committed only after the full scan is known to be complete. These lifetime and peak-memory issues are independent: persistent fields need explicit ownership, and temporary buffers need bounded lifetimes.

The semantic query graph is currently scaffolding rather than an active cache: `incremental_semantic_query_for_key`, `incremental_semantic_query_replace_dependencies`, and `incremental_semantic_query_invalidate_dependers` occur only at their definitions in the current `src/semantic` and `src/driver` tree. Current reuse is retained function facts and selective scan skipping; semantic query results and their dependencies are not yet reused. A real query-driven layer needs stable keys, complete read dependencies, reverse invalidation, and a cold path for missing or over-budget graph state. Key admission returns a sentinel on budget rejection while preserving the existing graph; dependency replacement returns `false` after preflight rejection. Invalidation now validates the full reverse closure before changing query statuses, so malformed-edge or worklist-budget failure leaves statuses unchanged but may advance visit stamps. A saturated graph continues rejecting new keys until explicitly reset. Future callers must treat sentinel/false results as a miss or abort, clear/reset corrupt or unusable state where required, and must never publish affected work as clean.

The opt-in semantic-session host is a separate semantic-only protocol. An exact hit still rereads and expands includes, tokenizes and parses the source, clones and reanchors retained facts, and runs the canonical semantic checks. The session currently reuses supported function facts and complete self-assignment findings; it does not reuse parse trees, query results, or LLVM/native artifacts. Ordinary CLI invocations construct a fresh session and release it after each compile, while the host retains its session between checks. The host now has independent spans for request total, include expansion, lex/parse, static preprocessing with any generated-source retokenization and reparse, incremental fact collection, and semantic passes. Inner spans overlap the request-total span and must not be summed as disjoint stages. This instrumentation creates boundaries for later measurement but is not itself performance evidence.

Source review of the Stage1 session finds a likely retained-edit allocation cost inside that fact-collection span: `incremental_collect_function_facts_with_session` clones the portable snapshot before comparing the current source with the saved source. The clone copies the serialized fact bytes and all function/direct-fact/grant/self-assignment arrays. An edit then collects a replacement snapshot and copies those facts into session storage; an exact hit still needs current-source anchors rebuilt before semantic checking. This is not yet isolated by a current-source profile. Measure clone, anchor rebinding, candidate matching, and storage separately; a later immutable fact view could remove some copies, provided per-request anchors remain isolated and the semantic gate can safely read session-owned facts.

A separate valid arm64 probe, `build/verification/local-slice-native.ll`, does show how contract-heavy source can affect unoptimized code shape. Its user-written `string_view_slice` has three large `ensure` formulas and repeated assertions. The saved IR function body contains 326 branch terminators, 147 integer comparisons, 99 phi nodes, and 10 allocas. Recompiling the saved IR with Homebrew LLVM 23.1.3 for `arm64-apple-darwin27.0.0` and `-mcpu=apple-m5`, then counting encoded instructions in the object, gives 1,589 instructions across 353 labeled blocks at `llc -O0`, with 698 `[sp]`-referencing instructions and a 1,152-byte local stack allocation plus a 16-byte callee-save pair. An O0 pass ablation (`opt -S -passes=...` followed by `llc -O0 -mtriple=arm64-apple-darwin27.0.0 -mcpu=apple-m5`) gives 1,571 instructions/680 stack references after `mem2reg`, 935/395 after `instcombine,simplifycfg`, and 770/266 after `mem2reg,instcombine,simplifycfg`; `mem2reg` alone barely changes code size, while combining arithmetic and simplifying the CFG remove much of the repeated control flow. Running `opt -O3 -S` followed by `llc -O3 -mcpu=apple-m5` reduces this to 37 encoded instructions (the symbol spans 148 bytes, or 37 AArch64 instructions) across four explicit branch-target labels (five blocks including entry) and removes stack accesses; default-CPU `llc -O3` emits 38 from the same optimized IR. The source repeats the same `start` normalization and `end` clamp in result-length contracts, pointer-offset contracts, and internal assertions; at O0, those expressions become separate load/phi/branch chains, while InstCombine and CFG simplification fold much of that work. This points to contract-expression sharing or a narrowly scoped IR canonicalization pass as a code-shape opportunity, but the fixture is deliberately contract-heavy and is not a compile-time hotspot profile or the runtime's short `string_view_slice` implementation. These pass counts establish emitted shape only; compilation time, runtime behavior, and source-level parity were not measured.

The initial retained-edit benchmark under `build/verification/incremental-pipeline-20261018/` measured a synthetic 256-function O0 workload with the lexical audit enabled in the retained path: fresh runs took about 405–413 ms total, while retained runs took about 496–502 ms. The retained path reused 255 bodies and checked one, but analysis rose from about 63 ms to 160–163 ms. That result included audit cost and should not characterize the default retained path.

The later source-isolated benchmark under `build/verification/incremental-audit-options-20261018/` separates fresh, retained, and retained-with-audit modes. Across three five-edit rounds, the medians were 421.69 ms fresh, 408.50 ms retained, and 527.43 ms retained with audit. Both retained modes reused 255 bodies and checked one. Retained total samples ranged from 402.7 to 511.7 ms while fresh ranged from 409.0 to 433.9 ms, so this synthetic benchmark does not establish a reliable end-to-end advantage, but it does show that removing audit from the default path avoids the earlier regression. The separate [benchmark record](incremental_compilation.md) documents source scope and limitations.


The 08:16 retained-analysis CPU profile attributed 0.39 s cumulative CPU (8.25% of the filtered profile) to `functionSyntaxEncoder.encode`; its allocation view also showed recursive encoding and publication copies. The 08:37 retained-pipeline CPU and allocation profiles are from the earlier audit-enabled path: they report 177.6 ms analysis and 259.6 MB allocated per edit, matching the later explicit `retained-audit` benchmark mode. In that audited O0 workload, the CPU profile attributes 2.85 s of 6.65 s sampled CPU (42.9%) to `LLVMTargetMachineEmitToFile`, 1.32 s (19.9%) cumulatively to semantic `Analyze`, 0.57 s (8.6%) to lexical-read publication, and 0.25 s (3.8%) flat to `functionSyntaxEncoder.encode`. The allocation profile attributes 1.51 GB (45.9%) cumulatively to lexical-read publication and 410 MB (12.5%) to the syntax encoder across the profiled run. This ranks object emission first in that audited O0 workload and exposes substantial audit and fingerprint costs; it cannot rank the current audit-disabled path. These profiles predate the audit split and the fingerprint reflection optimization below, and do not establish current self-hosted compiler costs.

A separate native-partition qualification is recorded under `build/verification/incremental-native-final-20261018/`. In its three pipeline rounds, the median object-emission stage fell from 400.7 ms fresh to 180.4 ms with the retained cache, reusing seven of eight partitions and emitting one. Median total edit time fell from 599.5 ms to 356.8 ms. The standalone partition benchmark reports 424.2 ms fresh versus 257.9 ms retained, with 74.5 ms IR generation, 21.7 ms merge, and 47.0 ms native emission on the retained path. This is meaningful evidence that object reuse can attack the largest measured stage, while the remaining IR generation, lowering, and module work stay in the path. The run manifest pins Core commit `1cb75ef0d05d8496fc69b07210d63952a2cc8772` and hashes 17 selected files; a live comparison now finds six of those files changed, so these numbers qualify only that recorded snapshot, not today's source. The manifest also limits the result to a short synthetic workload without final link or execution, and says the cache regenerates and optimizes the whole LLVM module.

## Follow-up: reduce fingerprint reflection overhead

In the Core compiler's retained-analysis encoder (`Elisa-core/compiler/src/semantic/incremental_function_identity.go`), the encoder now reads each value's type once and keeps immutable struct-field metadata in a process-wide cache, with a per-fingerprint map for local lookup. A fresh Core compiler build succeeded. Comparing the earlier local binary with the fresh build, ARM64 disassembly has one static `reflect.Value.typeSlow` call site in `functionSyntaxEncoder.encode`, down from eight, and its stack frame is 496 bytes instead of 624. `reflect.Type.Field` work is confined to the cold cache-miss helper. This is an assembly-shape improvement, not a measured runtime speedup: the binaries are not a controlled benchmark pair, no matched before/after edit benchmark was run, and the retained-edit workload still needs end-to-end qualification.

## Work to prioritize

1. Capture a fresh profile from a compiler product that matches the current tree. Record semantic, IR-generation, object-emission, and edit-to-executable wall time separately. The existing stage1 product and LLVM dump do not qualify.
2. Keep semantic reuse opt-in until an edit beats a fresh compile end to end. Replace repeated reflective AST serialization with parser-owned token/body spans or stable syntax-node identities for source-origin functions; retain cold fallback for synthetic or unsupported trees, plus exact dependency and option invalidation.
3. Requalify the native-partition cache after the six changed Core inputs are settled, preserving the same per-stage and whole-pipeline measurements. Then expose the verified path through normal compilation; the selected-snapshot benchmark is promising but does not establish current-source behavior.

The checked Stage1 compiler IR and Go assembly are diagnostic evidence, not a correctness or speedup qualification. The Core encoder change preserves the fingerprint's field order and names, but still needs a focused parity check and matched retained-edit benchmark before claiming a semantic or performance result.

The current static-generation preprocessor now keeps the output line map empty and uses the bytes-only copy path when it finds no expandable block. Ordinary files therefore avoid the line-map allocation and per-byte newline accounting used only for diagnostics after source expansion. This is a source-level fast-path change, not a measured speedup; it still needs parity coverage and a representative preprocessing measurement.
