# Incremental compilation bottleneck review

Reviewed 2026-10-18 from the local build notes, retained-edit benchmark, compiler LLVM dump, and the Go compiler's ARM64 disassembly.

## What the measurements show

The stage1 build profile in [build-speed-notes.md](build-speed-notes.md) is historical (base `2678ff10`), not a profile of the current working tree. It attributed 46% of samples to semantic analysis, 39% to LLVM IR generation, and 4% to O0 object emission. `check_region_storage_stability` accounted for 17.6% of samples; its `param_growth_rows` and `pgs_callee_fields` work accounted for 9.6% and 7.6%. The current `param_growth_summary.elisa` already has per-round dependency scheduling and indexed callee rows, so that old profile does not justify another isolated lookup tweak. A fresh matching stage1 profile is needed before ranking today's self-hosted hotspots.

The available `build/s1_driver.ll` is not usable for machine-code conclusions. Its `Semantic.check_region_storage_stability` wrapper only loads file fields and calls the declaration walker, but Clang rejects the module elsewhere: `%__packed_payload_108` receives an `i64` for an `i32` field at IR line 213991. Consequently the requested `-O0` assembly could not be generated from this dump. Do not use this stale dump as evidence about current generated code.

The saved `build/verification/current-seed-bb0b884b/` attempt is also not a current compiler result. Its 1,186-file input manifest was unchanged during the run, but Stage1 seeding stopped at the default 6 GiB RSS guard (`rc=125`, peak 6,443,352,064 bytes) after lexing in 565 ms and parsing in 2.204 s; it never reached semantic analysis or IR emission. Comparing that manifest with today's tree finds 630 changed inputs. Raising `ELISA_STAGE1_SEED_MAX_RSS_KB` may allow a later stable run to reach actionable diagnostics, but this artifact supplies none.

A separate valid arm64 probe, `build/verification/local-slice-native.ll`, does show how contract-heavy source can affect unoptimized code shape. Its user-written `string_view_slice` has three large `ensure` formulas and repeated assertions: `llc -O0` emits 1,585 instructions across 353 labeled blocks, with 698 stack-access lines and a 1,152-byte frame. `opt -O3 | llc -O3` reduces it to 36 instructions across four labeled blocks and removes stack accesses. This is a deliberately contract-heavy fixture, not the runtime's short `string_view_slice` implementation or a self-host profile. It shows LLVM cleaning up this specific O0 shape; it does not establish a current compile-time hotspot.

The initial retained-edit benchmark under `build/verification/incremental-pipeline-20261018/` measured a synthetic 256-function O0 workload with the lexical audit enabled in the retained path: fresh runs took about 405–413 ms total, while retained runs took about 496–502 ms. The retained path reused 255 bodies and checked one, but analysis rose from about 63 ms to 160–163 ms. That result included audit cost and should not characterize the default retained path.

The later source-isolated benchmark under `build/verification/incremental-audit-options-20261018/` separates fresh, retained, and retained-with-audit modes. Across three five-edit rounds, the medians were 421.69 ms fresh, 408.50 ms retained, and 527.43 ms retained with audit. Both retained modes reused 255 bodies and checked one. Retained total samples ranged from 402.7 to 511.7 ms while fresh ranged from 409.0 to 433.9 ms, so this synthetic benchmark does not establish a reliable end-to-end advantage, but it does show that removing audit from the default path avoids the earlier regression. The separate [benchmark record](incremental_compilation.md) documents source scope and limitations.


The 08:16 retained-analysis CPU profile attributed 0.39 s cumulative CPU (8.25% of the filtered profile) to `functionSyntaxEncoder.encode`; its allocation view also showed recursive encoding and publication copies. The 08:37 retained-pipeline CPU and allocation profiles are from the earlier audit-enabled path: they report 177.6 ms analysis and 259.6 MB allocated per edit, matching the later explicit `retained-audit` benchmark mode. In that audited O0 workload, the CPU profile attributes 2.85 s of 6.65 s sampled CPU (42.9%) to `LLVMTargetMachineEmitToFile`, 1.32 s (19.9%) cumulatively to semantic `Analyze`, 0.57 s (8.6%) to lexical-read publication, and 0.25 s (3.8%) flat to `functionSyntaxEncoder.encode`. The allocation profile attributes 1.51 GB (45.9%) cumulatively to lexical-read publication and 410 MB (12.5%) to the syntax encoder across the profiled run. This ranks object emission first in that audited O0 workload and exposes substantial audit and fingerprint costs; it cannot rank the current audit-disabled path. These profiles predate the audit split and the fingerprint reflection optimization below, and do not establish current self-hosted compiler costs.

A separate native-partition qualification is recorded under `build/verification/incremental-native-final-20261018/`. In its three pipeline rounds, the median object-emission stage fell from 400.7 ms fresh to 180.4 ms with the retained cache, reusing seven of eight partitions and emitting one. Median total edit time fell from 599.5 ms to 356.8 ms. The standalone partition benchmark reports 424.2 ms fresh versus 257.9 ms retained, with 74.5 ms IR generation, 21.7 ms merge, and 47.0 ms native emission on the retained path. This is meaningful evidence that object reuse can attack the largest measured stage, while the remaining IR generation, lowering, and module work stay in the path. The run manifest pins Core commit `1cb75ef0d05d8496fc69b07210d63952a2cc8772` and hashes 17 selected files; a live comparison now finds six of those files changed, so these numbers qualify only that recorded snapshot, not today's source. The manifest also limits the result to a short synthetic workload without final link or execution, and says the cache regenerates and optimizes the whole LLVM module.

## Follow-up: reduce fingerprint reflection overhead

In the Core compiler's retained-analysis encoder (`Elisa-core/compiler/src/semantic/incremental_function_identity.go`), the encoder now reads each value's type once and keeps immutable struct-field metadata in a process-wide cache, with a per-fingerprint map for local lookup. A fresh Core compiler build succeeded. Comparing the earlier local binary with the fresh build, ARM64 disassembly has one static `reflect.Value.typeSlow` call site in `functionSyntaxEncoder.encode`, down from eight, and its stack frame is 496 bytes instead of 624. `reflect.Type.Field` work is confined to the cold cache-miss helper. This is an assembly-shape improvement, not a measured runtime speedup: the binaries are not a controlled benchmark pair, no matched before/after edit benchmark was run, and the retained-edit workload still needs end-to-end qualification.

## Work to prioritize

1. Capture a fresh profile from a compiler product that matches the current tree. Record semantic, IR-generation, object-emission, and edit-to-executable wall time separately. The existing stage1 product and LLVM dump do not qualify.
2. Keep semantic reuse opt-in until an edit beats a fresh compile end to end. Replace repeated reflective AST serialization with parser-owned token/body spans or stable syntax-node identities for source-origin functions; retain cold fallback for synthetic or unsupported trees, plus exact dependency and option invalidation.
3. Requalify the native-partition cache after the six changed Core inputs are settled, preserving the same per-stage and whole-pipeline measurements. Then expose the verified path through normal compilation; the selected-snapshot benchmark is promising but does not establish current-source behavior.

The checked Stage1 compiler IR and Go assembly are diagnostic evidence, not a correctness or speedup qualification. The Core encoder change preserves the fingerprint's field order and names, but still needs a focused parity check and matched retained-edit benchmark before claiming a semantic or performance result.
