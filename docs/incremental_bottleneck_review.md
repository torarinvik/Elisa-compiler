# Incremental compilation bottleneck review

Reviewed 2026-10-18 from the local build notes, retained-edit benchmark, compiler LLVM dump, and the Go compiler's ARM64 disassembly.

## What the measurements show

The stage1 build profile in [build-speed-notes.md](build-speed-notes.md) is historical (base `2678ff10`), not a profile of the current working tree. It attributed 46% of samples to semantic analysis, 39% to LLVM IR generation, and 4% to O0 object emission. `check_region_storage_stability` accounted for 17.6% of samples; its `param_growth_rows` and `pgs_callee_fields` work accounted for 9.6% and 7.6%. The current `param_growth_summary.elisa` already has per-round dependency scheduling and indexed callee rows, so that old profile does not justify another isolated lookup tweak. A fresh matching stage1 profile is needed before ranking today's self-hosted hotspots.

Historical default-build measurements in [stage1_performance.md](stage1_performance.md) show a different priority from the O0 object-cache experiments: whole-module LLVM O2 took 92.7 seconds of a 134-second self-host build, and a later round measured 97 seconds of 143 seconds. The associated pass profile covered 2.03 million IR instructions and 9,350 functions; InstCombine was about 20% of pass time, followed by the Inliner at 7.6%. A parallel ThinLTO prototype reduced optimizer-plus-codegen wall time on a loaded host, but the resulting compiler failed runtime parity and was not adopted. These profiles are old Linux snapshots, not current-source measurements. They show why an O0 shard cache alone cannot address the historical default O2 bottleneck, and why O2 reuse needs an optimization boundary that preserves cross-function imports and passes runtime parity.

The available `build/s1_driver.ll` is not usable for machine-code conclusions. Its `Semantic.check_region_storage_stability` wrapper only loads file fields and calls the declaration walker, but Clang rejects the module elsewhere: `%__packed_payload_108` receives an `i64` for an `i32` field at IR line 213991. Consequently the requested `-O0` assembly could not be generated from this dump. Do not use this stale dump as evidence about current generated code.

The saved `build/verification/current-seed-bb0b884b/` attempt is also not a current compiler result. Its 1,186-file input manifest was unchanged during the run, but Stage1 seeding stopped at the default 6 GiB RSS guard (`rc=125`, peak 6,443,352,064 bytes) after lexing in 565 ms and parsing in 2.204 s; it never reached semantic analysis or IR emission. Comparing that manifest with today's tree finds 630 changed inputs. Raising `ELISA_STAGE1_SEED_MAX_RSS_KB` may allow a later stable run to reach actionable diagnostics, but this artifact supplies none.

The source-frozen semantic profile under `build/verification/frozen-seed-profile-bb0b884b/` is useful for allocation leads, but not as a current-source result: it pins the older Core revision `bb0b884b`, exits during semantic analysis before codegen, and reports 223.6 s elapsed. Its CPU profile is dominated by Go heap clearing (`runtime.memclrNoHeapPointers`, 39.5% flat), map assignment (15.1% cumulative), and `madvise` (11.1% flat). Its allocation profile attributes 3.32 GB to `cloneTrackedValueTypeWithSeenDepth`, 2.05 GB to `strings.Builder.WriteString`, 1.30 GB to `strings.FieldsFunc`, 1.15 GB to `abstractParamRegionRefState`, and 6.29 GB cumulatively to `smtCheckVCMulti`. These identify semantic allocation and GC pressure worth re-profiling after a successful, source-matched seed; they do not rank today's LLVM or object-emission path.

## Retained session memory and lifetime

The original session declarations had dynamic arrays and a dictionary without region parameters or per-field region annotations; qualifying only a function's `session` reference did not establish that nested storage survived request teardown. The current worktree now introduces `IncrementalSemanticSession[@r]` and a separate `IncrementalSemanticSessionSnapshot[@r]`, annotates retained collections `@r`, copies portable facts into that snapshot, and leaves invocation anchors in the request-owned snapshot. New controls now cover a generic struct with an empty `darray[...] @r` field that grows through the struct, reject a request-borrowed view stored in a session region, and drive a small-to-128-included-functions-to-same-large sequence through request teardown. The gate compiles the direct field control but does not execute its generated code; the live session sequence requires the repeated large request to hit with at least 100 eligible function bodies, all matched to retained facts. These controls have been reviewed statically but the gate has not yet been run, so the ownership change remains unvalidated by the compiler. The opt-in session remains a semantic-only host. The ordinary CLI now passes a fresh request-scoped session through its compile path, but discards it at request end and cannot reuse facts across separate invocations, so it is not yet an edit-to-executable speedup. Retain no token slices, AST-backed names, or other request views.

There is a separate request-peak issue: candidate scanning stages findings and then staged fact/anchor arrays, while edit replay also stages rebound anchors. A review estimate puts the peak near 176 bytes per finding before allocator growth when those buffers coexist. Reclaim candidate scratch in a nested region, or stream with rollback so a body is committed only after the full scan is known to be complete. These lifetime and peak-memory issues are independent: persistent fields need explicit ownership, and temporary buffers need bounded lifetimes.

The semantic query graph now has a private, session-owned key/evaluate/commit protocol with opaque generation-checked handles, exact byte comparisons, bounded dependency sets, and reverse invalidation. The session collector consults `SourceInput` and `FunctionBodyFacts` nodes on changed-source requests, and publishes their canonical byte projections after a successful snapshot store. A body query is attempted only after the trusted prior snapshot proves an exact declaration surface, cacheable prior record, and exact body match. A body hit restores canonical query bytes into the current request snapshot after validating them against the previous typed facts. If a graph lookup or restore misses, the collector still copies prior typed facts under the exact-surface and exact-body checks; it scans the current body only when that fallback is unavailable or invalid. The publisher still rebuilds and reevaluates the source query after collection. For body-query hits restored successfully, request-local markers let publication reacquire a fresh body-query handle and skip duplicate body copying, hashing, and evaluation only when graph generation, exact query key, body record span in the unchanged request snapshot, body result generation, SourceInput result generation, Green dependencies, and graph health still match. Markers retain request-local IDs and generation evidence, never query handles; graph clears and retries invalidate them. The `body_query_publish_skips` counter exposes this path. Source-value reconstruction and evaluation, plus all misses, remain on the existing path. Canonical direct-fact results are serialized and committed only on misses. This is an unmeasured work-reduction change, not a speedup claim. No source-matched retained-edit benchmark qualifies the graph path, and it has not passed parity controls. The parse and snapshot path remains authoritative.

`bodies_matched` and `body_facts_reused` remain aggregate counts. The collector now also reports `function_body_facts_restored`, `prior_snapshot_fact_fallbacks`, and `cold_body_scans`; `source_input_admitted` is true only when the source query hits and the exact trusted declaration surface also matches. The semantic-session control asserts both a body-fact graph restore and source-query admission on its inserted-line case. These counters make the route observable, but the control has not been run against a source-matched compiler, so they do not yet qualify correctness or speedup.

Per-value preflight guards are now present in the live source: the collector and publisher check the exact encoded `SourceInput` size before making its graph value copy, body lengths above 16 MiB skip graph copies, `ifq_query_evaluate` returns a miss before hashing an oversized input, and direct-fact result size is validated against the same per-value limit before serialization reserves or appends bytes. The typed snapshot remains the fallback for values rejected by these checks. The collector still assembles the proposed declaration surface needed for exact snapshot comparison. These per-value checks do not preflight aggregate graph admission: a permitted input copy or canonical result can still be materialized before commit rejects it against the 32 MiB logical value pool. If a publication attempt is rejected, including by aggregate capacity, the publisher clears the graph and retries once from the current committed snapshot; if the retry also fails, it leaves the graph empty and the typed-snapshot fallback remains authoritative. The per-value checks bound temporary input/result work, but these temporaries are outside the aggregate budget, and logical payload accounting does not bound allocator capacity retained across edits. A remaining-capacity preflight or span-based evaluator could reduce temporary peaks; a resettable region or explicit capacity accounting is needed to bound retained memory. Keep the graph opt-in. These guards have source review only and still need parity and retained-session performance evidence.

Key admission returns a miss on a cap rejection without mutating the graph. Commit validates candidate handles, exact dependency identity, committed result generations, and cycles before replacing the edge set. Logical value/aggregate overflow clears the graph; the publisher then makes the single rebuild retry described above, leaving it empty if publication fails again. Malformed adjacency and worklist overflow poison it so affected work cannot be published Green. Stale dependers become `PotentiallyDirty` and can return Green only after their direct dependencies are Green and their observed result generations are current. Dependency deduplication still uses bounded nested scans. `ifq_graph_within_limit` budgets logical counts for the key/value/node/edge pools, while `darray.reserve` can retain larger capacities and `ifq_clear_session_graph` clears/truncates without releasing those buffers. Persistent sessions keep graph evaluation/publication disconnected by default; the explicit `ELISA_STAGE1_INCREMENTAL_QUERY_GRAPH=1` opt-in publishes on cold starts and changed-source requests. The 32 MiB limit is a logical admission budget per graph generation; it does not include prior arena backing blocks, dictionary bucket tables, or pre-admission temporaries, so it is not a hard retained-session memory bound. Keep the graph opt-in until those allocations are charged across generations or it uses a resettable region. No parity or retained-edit performance comparison qualifies the graph path; misses and failed publication still use the exact typed-fact fallback where available and otherwise scan the current body.

The arena implementation confirms how retained capacity grows: `arena_da_reserve` and `arena_da_append_many` double capacity (`elisacore_std/collections.elisa:190-220,855-884`). `arena_realloc` extends a tail allocation in place when possible; only a non-tail move copies and retains the old backing until arena teardown (`elisacore_std/arena.elisa:1505-1523,1552-1567`). If each pool's capacity grows geometrically and never shrinks, retained array generations sum to less than twice its largest backing buffer; this is a conditional per-pool estimate, not yet a proven whole-graph bound. Truncating a pool must not subtract those bytes. Dictionary rehashing uses a current/spare stack ping-pong and returns the old table as spare, so count both tables rather than every historical generation (`elisacore_std/collections.elisa:1193-1216`). A hard retained-memory budget should charge actual growth allocations or use measured capacity, and should include any pre-admission temporaries separately.

The opt-in semantic-session host is a separate semantic-only protocol. An exact hit still rereads and expands includes, tokenizes and parses the source, clones and reanchors retained facts, resolves declarations, runs the parallel pass batches, and invokes the canonical whole-file checkers. The snapshot does let selected checkers skip narrower body work: Global-authority can skip bodies with no relevant direct facts or replay direct-call records, effect-source and ungranted-panic coverage can skip bodies proven to have no direct facts, and self-assignment checks can replay complete fact ranges. These are checker-specific walk reductions; semantic results are not cached, and the rest of the pipeline still runs. The private query graph restores canonical body-fact results into the current snapshot after checking them against the prior typed facts. It does not reuse parse trees or LLVM/native artifacts. Ordinary CLI invocations construct a fresh session and release it after each compile, while the host retains its session between checks. The host now has independent spans for request total, include expansion, lex/parse, static preprocessing with any generated-source retokenization and reparse, incremental fact collection, and semantic passes. Inner spans overlap the request-total span and must not be summed as disjoint stages. This instrumentation creates boundaries for later measurement but is not itself performance evidence.

Persistent `semantic-session` and `compile-session` hosts keep query-graph evaluation and publication disabled unless `ELISA_STAGE1_INCREMENTAL_QUERY_GRAPH=1` is set. The graph serves resolver reads through `resolver_name_classification`: `NameLookup` stores the composite `(known, module_only)` result from exact per-spelling surface facts, while `FunctionBodyFacts` continues to restore typed body facts. After declarations, aliases, imports, and region annotations are collected, the full-check pipeline eagerly finalizes collision-safe name and `(module, member)` indexes on every graph-active request, including requests with no NameLookup reads. This O(symbols + members + regions) prepass is included in whole-request timing but omitted from the chain counter. The NameLookup input records the explicit `name_indexed` gate, total and non-module symbol counts, module presence, member-row multiplicity, imported/current-module visibility, region presence, and the forced-builtin class; key schema 2 stores only current module and exact name, while identity/options mismatches reset the session graph. NameLookup no longer depends on the whole `SourceInput`; the SourceInput handle remains a request-generation/lifetime guard. Therefore unrelated declaration changes can leave an exact-name result green, while additions/removals, alias rows, visibility changes, and region-name changes alter the relevant input. If the surface index is unavailable or invalid, resolution uses the cold classifier and skips the query. Nonstandard declaration-resolution entry points do not finalize the surface and remain on that fallback path. Per-request reports expose NameLookup hits and classification-chain visits separately from body-fact restores/fallbacks. Both graph modes count rows visited by the fused NameLookup cold classifier. The retained-session paired harness checks that the call-heavy graph-on prime records cold visits and that exact-repeat/body-edit requests have fewer visits than graph-off. Raw NameLookup hits include duplicate same-request callee classification; the chain-visit reduction also combines same-request and retained-query reuse, so it does not isolate cross-request hit counts. The prime request is recorded separately and excluded from warm body-edit timing ratios. Its timed arms set `ELISA_STAGE1_INCREMENTAL_CACHE_REPORT=1`, which enables a counter increment for each symbol/member row visited in those fused classifier loops; direct qualified `Expr.Scope` probes are excluded. Graph-off visits more rows and pays more telemetry work, so current timing ratios may overstate graph-on gains; they are not production-equivalent until a counter-disabled timing arm exists. No fresh source-matched Stage1 paired run has shown a net end-to-end gain. The graph remains opt-in because its logical payload cap does not bound arena capacity retained across edits. `test/bench/incremental_fact_lookup/paired.py` launches fresh processes for its disk-sidecar cache and cannot measure this persistent-session comparison. The index/query changes have source review only; no build, parity run, or benchmark has verified them.
The chain counter covers only global symbol/member chains. The active graph path checks
lexical bindings linearly before every lookup, including hits, while region membership
comes from the finalized exact-spelling surface; only the cold fallback scans
`region_names`. Building that surface adds an O(symbols + members + regions) graph-on
prepass, included in whole-request timing but absent from the chain counter. The current
call-facts workload has neither locals nor region names, so it does not measure local
bound scans or the surface-build cost. Even when report output is disabled,
the hash-chain loops currently read the metrics-enabled flag and branch once per row;
a counter-free timing arm would still include that branch until tracked and plain lookup
loops are separated.
Bare module identifiers used as `Expr.Field` or namespace-call objects now pass through
`resolver_name_classification` and can contribute to NameLookup hits and classification
chain counters. Qualified `Expr.Scope` prefix/member probes still call
`name_is_module`, `ancestor_names_module`, `two_part_names_module`, and
`module_declares_member` directly; they are outside both the cache and counter. The
current paired fixture contains no module-field or qualified-path expressions and does
not measure them.

The checked-in semantic-session control includes a signature edit from `i64` to `bool`, requires zero query/snapshot restoration after the changed declaration surface, and compares a warm/cold diagnostic line. It does not compare the complete diagnostic set or assert the current-snapshot checker skip counters for Global-authority, effect-source, ungranted-panic coverage, and global-permission scanning. The control has not been run against a source-matched Stage1 compiler, so this coverage is static evidence only.

Source review of the Stage1 session finds a likely retained-edit allocation cost inside that fact-collection span: `incremental_collect_function_facts_with_session` clones the portable snapshot before comparing the current source with the saved source. The clone copies the serialized fact bytes and all function/direct-fact/grant/self-assignment arrays. An edit then collects a replacement snapshot and copies those facts into session storage; an exact hit still needs current-source anchors rebuilt before semantic checking. This is not yet isolated by a current-source profile. Measure clone, anchor rebinding, candidate matching, and storage separately; a later immutable fact view could remove some copies, provided per-request anchors remain isolated and the semantic gate can safely read session-owned facts.

A separate valid arm64 probe, `build/verification/local-slice-native.ll`, does show how contract-heavy source can affect unoptimized code shape. Its user-written `string_view_slice` has three large `ensure` formulas and repeated assertions. The saved IR function body contains 326 branch terminators, 147 integer comparisons, 99 phi nodes, and 10 allocas. In the saved O0 executable, the target-width `view_len.i64() != view.len` check also survives as `cmp x8, x8; b.eq` in `_string_view_slice` at `0x100000478`/`0x10000047c`; IR lines 373-380 load the copied `view_len` and the same `view.len` field. This is a concrete redundant check in this arm64 code shape, not a measured runtime cost. Recompiling the saved IR with Homebrew LLVM 23.1.3 for `arm64-apple-darwin27.0.0` and `-mcpu=apple-m5`, then counting encoded instructions in the object, gives 1,589 instructions across 353 labeled blocks at `llc -O0`, with 698 `[sp]`-referencing instructions and a 1,152-byte local stack allocation plus a 16-byte callee-save pair. An O0 pass ablation (`opt -S -passes=...` followed by `llc -O0 -mtriple=arm64-apple-darwin27.0.0 -mcpu=apple-m5`) gives 1,571 instructions/680 stack references after `mem2reg`, 935/395 after `instcombine,simplifycfg`, and 770/266 after `mem2reg,instcombine,simplifycfg`; `mem2reg` alone barely changes code size, while combining arithmetic and simplifying the CFG remove much of the repeated control flow. Running `opt -O3 -S` followed by `llc -O3 -mcpu=apple-m5` reduces this to 37 encoded instructions (the symbol spans 148 bytes, or 37 AArch64 instructions) across four explicit branch-target labels (five blocks including entry) and removes stack accesses; default-CPU `llc -O3` emits 38 from the same optimized IR. The source repeats the same `start` normalization and `end` clamp in result-length contracts, pointer-offset contracts, and internal assertions; at O0, those expressions become separate load/phi/branch chains, while InstCombine and CFG simplification fold much of that work. This points to contract-expression sharing or a narrowly scoped IR canonicalization pass as a code-shape opportunity, but the fixture is deliberately contract-heavy and is not a compile-time hotspot profile or the runtime's short `string_view_slice` implementation. These pass counts establish emitted shape only; compilation time, runtime behavior, and source-level parity were not measured.

## Follow-up: reduce fingerprint reflection overhead

In the Core compiler's retained-analysis encoder (`Elisa-core/compiler/src/semantic/incremental_function_identity.go`), the encoder now reads each value's type once and keeps immutable struct-field metadata in a process-wide cache, with a per-fingerprint map for local lookup. A fresh Core compiler build succeeded. Comparing the earlier local binary with the fresh build, ARM64 disassembly has one static `reflect.Value.typeSlow` call site in `functionSyntaxEncoder.encode`, down from eight, and its stack frame is 496 bytes instead of 624. The matching Go 1.27.2 `reflect.Value.Type` implementation takes an inline fast path for ordinary valid non-method values; `typeSlow` is reserved for invalid or method values, and the encoder returns before calling `Type` on invalid values. Thus the static call-site reduction does not show that `typeSlow` was running once per AST node. The measurable source-level candidate is narrower: the process-wide `sync.Map` is consulted once per distinct struct type per fingerprint, with repeated visits served from the per-fingerprint map, and `reflect.Type.Field` work occurs on cache misses. This remains code-shape evidence only; no sampled profile or matched repeated-fingerprint benchmark establishes its runtime cost or improvement.

### ARM64 shape of the default Core collector

The current Core `compiler/bin/elisac` binary reports Go 1.27.2 and VCS revision `907499e675cbe66c97e777a390bc15075f9386bc`, with `vcs.modified=true`. The `incremental_analysis_session.go` source file is clean at that revision. ARM64 objdump reports `Analyze.func3` at 4,384 bytes; its prologue checks a 720-byte stack threshold and sets the stack pointer 848 bytes lower. Its function-identity path calls `crypto/sha256.Sum256` after `runtime.growslice`/`runtime.memmove`, then performs `runtime.mapaccess1` for prior-owner membership. The source calls this collector closure twice per analysis, and derives each eligible function identity before filtering retained versus new owners, so this hashing/allocation shape repeats across both passes. Retained local declarations also hash a name while probing the previous key and hash it again while constructing that key. This is assembly evidence of repeated work, not a profile or measured latency result; the binary is marked modified, and a retained-edit benchmark is still needed to rank this against the AST traversal itself.

## Work to prioritize

1. Capture a fresh profile from a compiler product that matches the current tree. Record semantic, IR-generation, object-emission, and edit-to-executable wall time separately. The existing stage1 product and LLVM dump do not qualify.
2. Keep semantic reuse opt-in until an edit beats a fresh compile end to end. Replace repeated reflective AST serialization with parser-owned token/body spans or stable syntax-node identities for source-origin functions; retain cold fallback for synthetic or unsupported trees, plus exact dependency and option invalidation.
3. Requalify the native-partition cache against the current Core source, preserving the same per-stage and whole-pipeline measurements. Then expose the verified path through normal compilation; the selected-snapshot benchmark is promising but does not establish current-source behavior.

The checked Stage1 compiler IR and Go assembly are diagnostic evidence, not a correctness or speedup qualification. The Core encoder change preserves the fingerprint's field order and names, but still needs a focused parity check and matched retained-edit benchmark before claiming a semantic or performance result.

The mapped static-generation preprocessor leaves its output and line runs empty when it finds no expandable block, so ordinary driver calls keep the original source and avoid per-byte newline accounting. The separate bytes-only compatibility wrapper copies source bytes only for callers that need an output buffer. This is a source-level fast-path change, not a measured speedup; it still needs parity coverage and a representative preprocessing measurement.
